# Contributing to Nothing Phone (3a) Device Tree

Thank you for your interest in contributing to the LineageOS device tree for Nothing Phone (3a)! This guide will help you make quality contributions that benefit all users.

## Code of Conduct

- Be respectful and constructive
- Focus on technical merit
- Help others learn and improve
- Test your changes thoroughly
- Document your work clearly

## Getting Started

### Prerequisites

1. **Development Environment**
   - Ubuntu 20.04+ or similar Linux distribution
   - 300GB+ free disk space
   - 16GB RAM minimum (32GB recommended)
   - Git configured with your name and email

2. **Knowledge Requirements**
   - Android build system (Make/Soong)
   - Linux kernel basics
   - SELinux policy writing
   - Device tree structure
   - Git version control

3. **Hardware Access**
   - Nothing Phone (3a) device for testing
   - Unlocked bootloader
   - USB cable for ADB/Fastboot

### Setting Up Development Environment

```bash
# Clone the repository
git clone https://github.com/fuzailmansuri/android_device_nothing_asteroids
cd android_device_nothing_asteroids

# Create a development branch
git checkout -b feature/my-improvement

# Set up LineageOS build environment
repo init -u https://github.com/LineageOS/android.git -b lineage-23.2
repo sync -c -j$(nproc --all) --force-sync --no-clone-bundle --no-tags
```

## Types of Contributions

### 1. Bug Fixes

**Process**:
1. Verify the bug exists and is reproducible
2. Check if it's already reported/fixed
3. Identify root cause
4. Create minimal fix
5. Test thoroughly
6. Document the fix

**Example**: Fixing audio HAL crash during Bluetooth connection

### 2. Feature Additions

**Process**:
1. Discuss in GitHub Issues first
2. Ensure feature fits LineageOS philosophy
3. Check if similar feature exists upstream
4. Implement with minimal changes
5. Add documentation
6. Test all use cases

**Example**: Adding support for additional NFC chip variant

### 3. Performance Improvements

**Process**:
1. Measure current performance (benchmarks, profiling)
2. Identify bottleneck
3. Implement optimization
4. Measure improvement
5. Ensure no functionality regression
6. Document performance gains

**Example**: Optimizing kernel module load order for faster boot

### 4. Documentation Updates

**Process**:
1. Identify documentation gap or error
2. Research correct information
3. Write clear, concise documentation
4. Add examples where helpful
5. Proofread for clarity

**Example**: Adding troubleshooting section to TESTING.md

### 5. Hardware Support

**Process**:
1. Verify hardware variant exists
2. Obtain hardware specifications
3. Add device tree overlay if needed
4. Update configurations
5. Test on actual hardware
6. Document variant differences

**Example**: Adding support for different fingerprint sensor variant

## Contribution Workflow

### 1. Fork and Branch

```bash
# Fork the repository on GitHub first

# Clone your fork
git clone https://github.com/YOUR_USERNAME/android_device_nothing_asteroids
cd android_device_nothing_asteroids

# Add upstream remote
git remote add upstream https://github.com/fuzailmansuri/android_device_nothing_asteroids

# Create feature branch
git checkout -b feature/descriptive-name
```

### 2. Make Changes

**Follow these guidelines**:

- **Minimal Changes**: Only modify what's necessary
- **Code Style**: Match existing code style in the file
- **Comments**: Add comments for complex logic
- **Commit Messages**: Write clear, descriptive commit messages

**Commit Message Format**:
```
component: Brief description (50 chars or less)

Detailed explanation of what and why, not how.
Wrap at 72 characters.

Fixes: #issue_number
Test: Description of how you tested
Change-Id: (generated by git hook)
```

**Example**:
```
audio: Fix microphone noise during calls

The audio HAL was not properly configuring the noise suppression
module, causing background noise during phone calls. This adds
the missing configuration for the secondary microphone path.

Fixes: #42
Test: Made multiple calls with different background noise levels
Change-Id: I1234567890abcdef1234567890abcdef12345678
```

### 3. Test Your Changes

**Required Tests**:
- [ ] Device boots successfully
- [ ] Feature/fix works as intended
- [ ] No new SELinux denials
- [ ] No new warnings in build
- [ ] Related features still work (no regression)

**Use Testing Guide**:
```bash
# Run relevant tests from TESTING.md
# See TESTING.md for comprehensive test procedures
```

### 4. Commit and Push

```bash
# Stage your changes
git add -A

# Commit with descriptive message
git commit -s

# Push to your fork
git push origin feature/descriptive-name
```

**Note**: The `-s` flag adds a "Signed-off-by" line, certifying you wrote the code or have the right to submit it.

### 5. Create Pull Request

1. Go to GitHub repository page
2. Click "New Pull Request"
3. Select your branch
4. Fill out the PR template:
   - **Title**: Clear, concise description
   - **Description**: What, why, and how
   - **Testing**: How you tested the changes
   - **Screenshots**: If UI changes
   - **Related Issues**: Link any related issues

**PR Template**:
```markdown
## Description
Brief description of changes

## Motivation and Context
Why is this change needed? What problem does it solve?

## Testing Done
- [ ] Built successfully
- [ ] Boot test passed
- [ ] Feature tested on device
- [ ] No regressions observed

## Screenshots (if applicable)
Add screenshots for UI changes

## Types of Changes
- [ ] Bug fix (non-breaking change which fixes an issue)
- [ ] New feature (non-breaking change which adds functionality)
- [ ] Breaking change (fix or feature that would cause existing functionality to change)

## Checklist
- [ ] My code follows the code style of this project
- [ ] My change requires a change to the documentation
- [ ] I have updated the documentation accordingly
- [ ] I have tested on actual hardware
```

### 6. Code Review Process

**What to expect**:
1. Maintainers will review your PR
2. They may request changes
3. Address feedback promptly
4. Push updates to the same branch
5. Once approved, PR will be merged

**Responding to Feedback**:
- Be receptive to constructive criticism
- Ask questions if feedback is unclear
- Make requested changes or explain why you disagree
- Update PR description if scope changes

## Coding Standards

### Makefile/Blueprint

```makefile
# Use consistent formatting
PRODUCT_PACKAGES += \
    package1 \
    package2 \
    package3

# Group related items
# Audio
PRODUCT_PACKAGES += \
    audio.primary.volcano \
    audio.usb.default

# Camera
PRODUCT_PACKAGES += \
    camera.volcano
```

### SELinux Policy

```
# Use clear, descriptive type names
type hal_glyph_default, domain;

# Group related allow rules
# File access
allow hal_glyph_default sysfs_leds:dir r_dir_perms;
allow hal_glyph_default sysfs_leds:file rw_file_perms;

# Add comments for non-obvious rules
# Allow Glyph HAL to control LED brightness
allow hal_glyph_default sysfs_leds:file { write };
```

### Shell Scripts

```bash
#!/bin/bash
# SPDX-FileCopyrightText: 2025 The LineageOS Project
# SPDX-License-Identifier: Apache-2.0

# Use set -e to fail on errors
set -e

# Use meaningful variable names
DEVICE_TREE_PATH="${ANDROID_BUILD_TOP}/device/nothing/asteroids"

# Quote variables
echo "Device tree path: ${DEVICE_TREE_PATH}"
```

### Device Tree (DTS)

```dts
// Use consistent indentation (tabs)
&i2c_0 {
	touchscreen@5d {
		compatible = "goodix,gt9886";
		reg = <0x5d>;
		// Add comments for non-standard properties
		interrupt-parent = <&tlmm>;
		interrupts = <21 IRQ_TYPE_EDGE_RISING>;
	};
};
```

## Specific Contribution Areas

### Audio HAL Changes

**Requirements**:
- Test all audio scenarios (speaker, earpiece, Bluetooth, headphones)
- Verify no distortion or noise
- Check audio routing works correctly
- Test microphone input

**Key Files**:
- `audio/mixer_paths_volcano_qrd.xml`
- `audio/audio_policy_configuration.xml`
- `sepolicy/vendor/hal_audio.te`

### Kernel Changes

**Requirements**:
- Follow Linux kernel coding style
- Test with GKI compliance
- Ensure module loading works
- No new build warnings

**Key Files**:
- `BoardConfig.mk` (TARGET_KERNEL_CONFIG)
- `modules.load.*` files
- `KERNEL_MODULES.md` documentation

### Display/Graphics Changes

**Requirements**:
- Test all refresh rates (60Hz, 120Hz)
- Verify color accuracy
- Check rotation works
- Test AOD (Always-On Display)

**Key Files**:
- `configs/display_id_asteroids.xml`
- `rro_overlays/AsteroidsFrameworksOverlay/`

### Security Changes

**Requirements**:
- Maintain SELinux enforcing
- No new denials
- Follow least-privilege principle
- Document policy rationale

**Key Files**:
- `sepolicy/vendor/*.te`
- `sepolicy/public/*.te`
- `sepolicy/private/*.te`
- `SELINUX.md` documentation

## Security Guidelines

### Never Commit

- **Secrets**: API keys, passwords, tokens
- **Personal Data**: Email addresses, phone numbers
- **Proprietary Code**: Vendor-specific closed source code
- **Binary Blobs**: Large binary files (use Git LFS or external hosting)

### Security Best Practices

1. **Review Changes**: Double-check your commits
2. **Use Test Keys**: Don't commit production signing keys
3. **Validate Input**: Sanitize user input in scripts
4. **Follow SELinux**: Don't disable SELinux
5. **Update Dependencies**: Keep vendor blobs current

## Release Process

### Versioning

Device tree follows LineageOS version:
- **Major**: LineageOS version (23 = Android 16)
- **Minor**: Point release (23.1, 23.2)

### Tagging

Tags are created for stable releases:
```bash
git tag -a lineage-23.2-asteroids-v1.0 -m "Stable release for LineageOS 23.2"
git push origin lineage-23.2-asteroids-v1.0
```
